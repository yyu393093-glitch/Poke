# 文档解析板块 · 独立开发清单

> **归属**：这是 **Task 02 的新增板块**，由负责 Task 02 的人**独立完成**，不拆三人。
>
> **配套**：[文档解析板块-spec.md](./文档解析板块-spec.md) —— 字段名、接口、JSON Schema 全以它为准。

---

## 1. 开发顺序（按依赖，只能顺着做）

```
第一步 本地存储+上传  →  第二步 模型接入  →  第三步 推荐引擎  →  第四步 查询接口+前端
（先能存文件）          （再能解析）          （再能推荐分工）        （最后能给人看）
```

> 为什么是这个顺序：解析要先把上传的文件存下来、读出文本；推荐引擎要调第二步的模型；前端要调前三步的接口。一个人做，从上往下推进，不跳步。

---

## 2. 每一步要做什么

### 第一步 · 本地存储 + 文件上传

| # | 事项 | 产出 |
|---|---|---|
| 1 | JSON 文件读写封装（`data/store.json`） | `server/store.js`：读/写 `documents`、`parses`、`orgChart` |
| 2 | 文件上传（multer 存 `data/uploads/`） | `POST /api/doc/upload` |
| 3 | 文本提取（`.txt/.md/.json` 直接读；PDF/Word 可后置） | 上传后返回 `documentId` |

### 第二步 · 模型接入层（DeepSeek）

| # | 事项 | 产出 |
|---|---|---|
| 1 | 把 spec 第 6 节 JSON Schema 写成 JS 常量 | `server/parseClient.js` 里的 `POKE_DOC_SCHEMA` |
| 2 | 封装 DeepSeek 调用（`chat/completions` + `json_object` mode） | `parseDocument(text)` / `parseOrgChart(text)` |
| 3 | 实现 `POST /api/doc/parse` | 收 `documentId` 或 `text` → 调模型 → 结果写 `parses` 数组 |
| 4 | JSON 清洗修复 | 提取 `{…}`、去代码围栏、修尾逗号、失败重试一次 |
| 5 | 处理「没配 key」 | 读不到 `server/.env` → 返回 `{ error: "未配置模型" }` |

### 第三步 · 推荐分工引擎

| # | 事项 | 产出 |
|---|---|---|
| 1 | 实现 `POST /api/org/import` | 收组织架构文档 → 调 `parseOrgChart` → 写 `orgChart` 对象 |
| 2 | 实现规则引擎 | `server/assignmentEngine.js`：module 匹配 owner、依赖通知下游、跨部门对齐、去重 |
| 3 | 实现 `POST /api/assignment/recommend` | 收文档 → 调 `parseDocument` → 规则补全去重 → 返回推荐分工 |

### 第四步 · 查询接口 + 前端

| # | 事项 | 产出 |
|---|---|---|
| 1 | `GET /api/doc/list` + `GET /api/doc/:id` | 历史解析记录列表 / 单条结果 |
| 2 | 文档上传/粘贴页 + 结果展示 | `src/pages/DocParsePage.jsx` + `src/components/DocParsePanel.jsx` |
| 3 | 结果区三块：人员 / 任务 / 依赖 + 推荐分工卡片 | 同上 |
| 4 | 推荐分工卡片按 `action` 上色 | review 蓝 · align 橙 · notify 灰 · assign 绿 |
| 5 | loading / 错误 / 空结果三种状态 | 同上 |

---

## 3. 边界（独立开发也别忘了）

- 新文件集中在 `server/`（store.js、parseClient.js、assignmentEngine.js、路由）和 `src/`（DocParsePage、DocParsePanel），**不改**已有 8 个 Task 02 接口
- 存储用 JSON 文件 `data/store.json`，**不引入数据库**、不引入迁移工具
- API key 只进 `server/.env`，**不进 git**、不进前端
- 只调 DeepSeek（模型 ID 默认 `deepseek-v4-flash`，以官方为准）
- 不接真实飞书/企微/钉钉（H1 不变），只跑本地（H3 不变）
- 上传文件大小限制（如 10MB）

## 4. 避坑清单

| # | 坑 | 解法 |
|---|---|---|
| 1 | 模型吐的字段名和 Schema 对不上 | `json_object` mode + prompt 里贴 Schema，Schema 写成常量只认一处 |
| 2 | 模型编造文档里没有的人/任务 | prompt 强调「没有就空数组」+ 规则引擎再过滤一遍 |
| 3 | 坏 JSON 让后端崩 | 清洗修复 + try/catch，失败写 `parses.status = failed` |
| 4 | 文档超长塞爆请求 | 超 32k 字符截断，保留开头摘要 + 关键段落 |
| 5 | JSON 文件并发写坏 | 读写都在内存里改，再整体 `writeFileSync` 落盘 |

---

## 5. 验收标准

照 [文档解析板块-spec.md](./文档解析板块-spec.md) 第 12 节逐条过：

1. 上传 `.md/.txt` → 文件落盘 `data/uploads/`，`documents` 数组多一条
2. 解析 → 返回合法 JSON，`parses` 数组多一条 `success`
3. 贴空/无关文档 → 空 `tasks/people`，不报错不瞎编
4. 贴组织架构文档 → `orgChart` 抽出部门 + 汇报线
5. 贴带模块+负责人的任务文档 → 给出 assign/review 推荐
6. `GET /api/doc/list` 能列历史，`GET /api/doc/:id` 能看单条
7. mock 坏 JSON → 清洗修复后仍能解析或优雅报错
8. 没配 key → 返回「未配置模型」，前端提示不白屏
9. 前端上传 → 结果区展示人员/任务/依赖/推荐分工卡片，控制台无报错
